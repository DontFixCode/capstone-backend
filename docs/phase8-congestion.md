# Phase 8 — 버스 예상 혼잡도 (측정 부분)

관리자가 내려받은 승하차 원본 파일로 노선 구간별 "평소 이 시간대 예상" 혼잡 단계를 계산해 경로 후보와 정류소 도착 목록에 내보낸다.
값은 과거 승하차 집계에서 계산한 추정이며 실시간 관측이 아니다. 실측 대조 전이므로 추정 정확도는 **검증 대기**다.

설계 초안은 Notion "혼잡도 테이블 설계 (ridership_counts · congestion_profiles)"와 Development Phase의 Phase 8이다.
2026-11-26에 실제 원본 파일과 서버 DB로 대조해 초안과 다르게 정한 점은 아래 [초안과 다른 점](#초안과-다른-점)에 있다.

## 구현 범위

| 초안의 개발 순서 | 상태 |
|---|---|
| 1. `ridership_counts` DDL·입력·정류장 대응 | 구현 |
| 2. `congestion_profiles` DDL·집계 | 구현 |
| 3. 통과 횟수 | 위치 관측으로 실제 지나간 차량을 센다(`observed`). 관측이 모자란 칸은 배차간격(`timetable`) |
| 4. 조회·표시 | 경로 후보의 버스 구간, 정류소 도착 목록에 구현 |
| 5. 혼잡 비용 반영 | 구현. 추천 비용의 내시균형 bias로 더한다(가중치 설정이 있을 때만) |
| 5. 안내 인원 반영 | 구현. 앱이 안내 중인 다른 사용자의 탑승을 검색 후보의 1대당 재차에 더한다 |
| 5. 균형 시뮬레이션 | 구현(오프라인 스크립트 `scripts/simulate_equilibrium.py`, 로짓 선택·연속평균법) |

## 원본 파일 내려받기

대전교통빅데이터플랫폼 → 버스-승하차지표 → 분석지표 **노선별정류장승하차인원**.

- 일자선택은 **일별**로 두고 기간을 고른다. 월별로 받은 파일은 일자를 알 수 없어 거부된다.
- 노선 하나, 시간대 하나를 골라 조회한 뒤 **엑셀저장**으로 받는다. 시간대마다 파일을 따로 받는다.
- 표출단위는 **정류장별**이다.
- 받은 파일은 이름만 바꿔도 되고 내용은 고치지 않는다. 엑셀에서 열어 다시 저장하면 형식이 바뀌어 거부된다.
- 플랫폼 집계가 끝나지 않은 최근 일자는 값이 덜 차 있다. 같은 노선·일자·시간·순번이 이미 있으면 건너뛰므로 나중에 올려도
  바뀌지 않는다. 집계가 끝난 일자만 올린다.
- 한 파일에 여러 시간대를 함께 받아도 된다(확인한 파일: 일자마다 05~23시 19개 시간대와 합계 행 하나). 입력 결과의
  `days_by_hour_count`로 시간대 수가 다른 날을 확인한다.

확인한 파일 형식(301번 2026-01-01~10-22 09시, 2026-09-17~11-15 05~23시): 확장자는 `.xls`지만 내용은 HTML 표 하나다. 머리글은
`일자, 노선, 시간, 순번, 정류장, 단순승차, 하차, 환승승차`이고 정류장 칸은 `이름(정류소 번호)`다. 일자마다 `합계` 행이 있다.

## 실행

DDL은 `migrations/13_congestion.sql`이다. 적용 전에는 혼잡 정보가 모두 `unavailable`로 나가고 다른 기능은 그대로 동작한다.

```sh
uv run python -m scripts.import_ridership import data/ridership/*.xls            # 검증·대응 결과와 예상 집계(저장 안 함)
uv run python -m scripts.import_ridership import data/ridership/*.xls --execute  # 원본 누적 후 해당 노선 다시 집계
uv run python -m scripts.import_ridership aggregate --route-no 301 --execute     # 한 노선만 다시 집계
uv run python -m scripts.import_ridership status                                 # 노선별 입력·집계 현황과 적용 설정
```

- 입력은 파일 단위로 검증한다. 머리글·날짜·시간·인원·합계 검산 중 하나라도 틀리면 그 파일은 한 행도 저장하지 않고 사유를 준다.
- 워커는 정적 갱신(하루 1회) 뒤에 원본이 있는 노선을 모두 다시 집계한다. 정류소 순서 변경과 집계 창 이동이 함께 반영된다.
- 원본이 입력된 노선은 워커가 위치를 상시 수집한다(실제 통과 횟수를 세는 자료). 노선 하나에 수집 간격(기본 600초)마다
  TAGO 위치 조회 1건, 하루 144건이 든다. 관측이 쌓이기 전에는 배차간격 값이 쓰인다.

## 설정 (`.env.api`)

근거 없는 기본값을 두지 않는다. 비어 있으면 그 값이 필요한 기능이 사유와 함께 멈춘다.

| 설정 | 뜻 | 비어 있을 때 |
|---|---|---|
| `BACKEND_CONGESTION_WINDOW_MONTHS` | 집계에 쓰는 직전 n개월 | 집계를 실행하지 않음 |
| `BACKEND_CONGESTION_SEATS`, `BACKEND_CONGESTION_CAPACITY` | 1대당 좌석 수·정원 | 단계 미산출(`congestion_not_configured`) |
| `BACKEND_CONGESTION_MIN_SAMPLE_DAYS` | 이보다 표본 일수가 적으면 p80 미산출·`lowConfidence`. 위치 관측 일수가 이보다 적은 요일유형·시간대는 배차간격으로 대신 | 2일 이상이면 p80 계산, `lowConfidence` 표시 없음, 관측은 1일만 있어도 사용 |
| `BACKEND_CONGESTION_HOLIDAYS` | 공휴일(`YYYY-MM-DD`, 쉼표 구분) | 일요일만 holiday |
| `BACKEND_CONGESTION_COST_WEIGHTS` | 단계별 탑승시간 가중치 5개(`empty`부터 `very_crowded` 순, 각 1 이상, 단계가 높을수록 크거나 같게) | 혼잡을 순위에 반영하지 않음(bias 0) |

## 계산

```txt
L[k] = max(0, L[k-1] + 총승차[k] - α × 하차[k])      k는 원본 순번, L[0] = 0
α    = Σ총승차 ÷ Σ하차                               같은 노선·일자·시간대의 합계
1대당 재차 = 흐름 ÷ 시간당 통과 횟수                  흐름은 flow_p80 우선, 없으면 flow_mean
시간당 통과 횟수 = 그 구간을 실제로 지나간 차량 수    위치 관측(observed). 관측이 모자라면 60 ÷ 배차간격(분)
```

- 통과 횟수는 노선 위치 관측에서 센다. 같은 차량의 연속 관측 두 건 사이에 지나간 구간마다 1을 더하고, 그 시간대에 관측이
  덮은 시간으로 나눈 뒤 요일유형·시간대별로 관측한 날들을 평균한다. 구간마다 따로 세므로 첫차·막차 무렵처럼 차량이 아직
  닿지 않은 구간은 0에 가깝게 나오고, 시간당 1대 미만인 구간·시간대는 1대당 재차를 만들지 않는다(`congestion_trips_unknown`).
- 배차간격은 요일별 값 하나뿐이라 시간대별 차이를 담지 못한다. 301번 위치 관측(평일 1~2일분)에서는 낮 시간대가 시간당
  약 8대, 16~18시가 5~6대였다(배차간격 기준 7.5대). 정체로 한 바퀴가 길어지면 같은 차량 수로도 통과 횟수가 줄어든다.

- `L[k]`는 그 시간대에 k번째 정류소를 출발한 직후 구간을 지난 모든 차량의 재차 합이다.
- 요일유형은 `weekday` / `saturday` / `holiday`(일요일·공휴일)다.
- 단계는 좌석 수 S와 정원 C가 경계다: `empty` ≤ 0.2S, `relaxed` ≤ S, `normal` ≤ (S+C)/2, `crowded` ≤ C, `very_crowded` > C.
- 버스 구간(승차~하차)은 타고 가는 구간 가운데 1대당 재차가 가장 큰 구간의 값으로 나타낸다.
- 해당 요일유형·시간대의 행이 없으면 같은 요일유형의 앞뒤 시간대 평균, 그다음 평일의 같은 시간대로 대신하고 `fallback`에 남긴다.

α를 하루 합계가 아니라 시간대별로 구하는 이유(301번 2026-09-17~11-15 전체 시간대, 평일 42일 평균): 하루 합계 α(중앙값 1.40)로는
7시에 종점까지 시간당 약 407명이 남고(오는 방향 최대 632명) 9시에는 지나치게 깎인다(최대 249명). 시간대별 α는 7시 종점 잔여가
약 22명, 최대 402명이고 9시 최대는 282명이다. 회차지(50번째)에서 남는 흐름은 시간대별 α로 시간당 1~24명이다. 팀원 분석기처럼
방향·시간대별로 나눠 회차지에서 0으로 맞추는 방식과는 최대 구간 값이 2~6% 차이다(회차지 위치를 노선마다 확인해야 해 쓰지 않았다).

## 순위 반영 (내시균형 bias)

```txt
추천 비용 = 선택한 모드의 이동시간 + 내시균형 bias
내시균형 bias = Σ 버스 구간의 탑승시간 × (그 구간 혼잡 단계의 가중치 − 1)
```

- 가중치는 `BACKEND_CONGESTION_COST_WEIGHTS`다. 초안의 시작값 `1.0, 1.0, 1.2, 1.5, 2.0`이면 20분을 타는 구간이 `crowded`일 때
  10분, `very_crowded`일 때 20분이 비용에 더해진다. `empty`·`relaxed`는 더해지지 않는다.
- 구간의 단계는 응답의 `legs[].congestion`과 같은 값이다(승차 예상 시각의 요일유형·시간대, 타는 구간 중 가장 붐비는 구간).
  가장 붐비는 구간의 단계를 그 버스 구간의 탑승시간 전체에 적용한다.
- 순위 모드를 따로 두지 않는다. nominal·expected 어느 모드든 그 모드의 시간에 더하고 비용 → 환승 횟수 → 도보시간 → 후보 ID
  순으로 정렬한다. 배차간격 예상 후보를 실시간 후보 뒤에 두는 규칙은 그대로다.
- 혼잡 정보가 없는 구간(집계가 없는 노선, 해당 시간대 없음, 통과 횟수 없음)은 더하지 않는다. 붐비지 않는 것으로 본 것과
  같아서, 원본을 입력한 노선만 비용이 붙는다. 검색 요약 `summary.congestion_bias.candidates_with_unknown_leg`에 그런 후보 수를 남긴다.
- 후보 응답의 `cost`에 계산 결과가 나간다. 비용이 붙은 후보는 `rankingReasonCodes`에 `congestion_bias_applied`가 들어간다.

```json
"cost": { "timeSeconds": 2140.0, "equilibriumBiasSeconds": 300.0, "costSeconds": 2440.0 }
```

- 이동 중 재계산의 경로 변경 판단(`decide_change`)은 남은 시간만 비교하며 혼잡 비용을 쓰지 않는다.
- 검색 순위는 붐비는 경로의 비용을 올리는 방식이며, 이용자들의 선택이 바뀐 뒤의 혼잡을 다시 계산하지는 않는다. 그 계산은
  아래 균형 시뮬레이션에서 오프라인으로 한다.

### 안내 인원 반영

앱이 지금 안내 중인 탑승(활성 이동의 선택 경로에서 아직 끝나지 않은 버스 구간)을 검색 후보의 1대당 재차에 더한다. 단계와
혼잡 비용은 더한 값으로 정한다.

```txt
1대당 재차 = 집계 기준 재차 + 안내 인원
안내 인원  = 같은 차량으로 안내한 탑승 수 + (차량을 모르는 탑승 수, 같은 날짜·시간대) ÷ 시간당 통과 횟수
```

- 같은 노선·패턴에서 타는 구간이 겹칠 때만 센다. 차량번호가 서로 다르면 더하지 않는다. 한쪽이라도 차량을 모르면 그 시간대
  차량에 고르게 탄다고 본다.
- 계획한 하차 시각이 지난 탑승과 이미 하차한 구간은 세지 않는다(종료하지 않고 방치된 이동이 계속 세어지지 않게 한다).
- 검색을 요청한 사용자 자신의 이동은 세지 않는다. 정류소 도착 목록에는 더하지 않는다.
- 더한 값은 `legs[].congestion.guidedRiders`에 나가고, 검색 요약 `summary.congestion_bias.guided_rides`에 읽은 탑승 수를 남긴다.
- 선택 당시의 계획 차량·시각을 쓴다. 그 뒤 차량을 놓치거나 바꿔 탄 것은 반영하지 않는다.

### 균형 시뮬레이션 (오프라인)

저장된 검색 하나의 순위 후보를 대상으로, 같은 출발·도착을 한 시간에 N명이 검색한다고 두고 균형 분포를 구해 지금 분포와
비교한다. DB에 쓰지 않고 외부 API도 호출하지 않는다.

```sh
uv run python -m scripts.simulate_equilibrium --search-id <검색 ID> --demand-per-hour 200 --theta 0.01
```

```txt
구간 재차(1대당) = 집계 기준 재차 + (그 구간을 지나는 후보들의 선택 인원 합) ÷ 시간당 통과 횟수
후보 비용        = 이동시간 + Σ 버스 구간 탑승시간 × (혼잡 단계 가중치 − 1)
선택 비율(로짓)  = exp(−θ × 비용) ÷ Σ exp(−θ × 비용)
연속평균법       = x[n+1] = x[n] + (y[n] − x[n]) ÷ n,   y[n] = N × 선택 비율(x[n]일 때의 비용)
```

- 결과는 후보별로 세 분포를 준다: 모두 1위 후보를 고를 때(`share_all_to_best`), 지금 비용으로 로짓 선택할 때(`share_before`),
  균형(`share_at_equilibrium`). `max_share`로 한 후보에 쏠리는 정도를 비교한다.
- 같은 정적 경로를 차량만 바꿔 타는 조합은 순위가 가장 높은 하나만 쓴다.
- N(`--demand-per-hour`)과 θ(`--theta`, 1/초)는 근거 있는 값이 없어 실행할 때 준다. θ = 0.01이면 비용이 100초 낮은 후보를
  약 2.7배 더 고른다.
- 집계가 없는 노선은 기준 재차를 0으로 두고 통과 횟수를 노선 배차간격(또는 `--assume-trips-per-hour`)으로 채우며, 후보별
  `assumed`에 남긴다. 통과 횟수도 없으면 그 구간은 혼잡 비용 없이 둔다.
- 혼잡 가중치가 단계마다 뛰는 계단 함수라 분포가 단계 경계에 머물며 정확히 수렴하지 않을 수 있다. `converged`와 `gap`을
  그대로 보고한다.

## 응답

경로 후보의 버스 구간(`legs[].congestion`)과 정류소 도착 목록(`items[].congestion`)에 같은 형식으로 나간다. 후보에는 당시 값과
설정 버전을 복사해 두므로 이동 선택 스냅샷에도 남는다.

```json
{
  "kind": "typical_for_time", "status": "available", "level": "crowded", "levelIndex": 4,
  "loadPerVehicle": 41.6, "guidedRiders": 0.0, "basis": "p80", "stopSeq": 75, "dayType": "weekday", "hour": 9,
```

## 초안과 다른 점

| 초안 | 구현 | 이유 |
|---|---|---|
| 엑셀 파일을 올린다 | HTML 표 형식 `.xls`만 받는다. 실제 엑셀 형식은 거부 | 플랫폼 원본이 HTML 표다. 확인하지 않은 형식은 받지 않는다 |
| `total_board_count` NOT NULL, `board_count`·`transfer_board_count` NULL 허용 | 세 값(단순승차·하차·환승승차) NOT NULL, 총승차는 생성 열 | 원본에 총승차 열이 없다 |
| `source_stop_id` NOT NULL, `source_stop_order` NULL 허용, 고유 키에 둘 다 포함 | 순번 NOT NULL(정수), 정류소 번호 NULL 허용, 고유 키는 (노선, 일자, 시간, 순번) | 순번은 항상 있고 정류소 번호가 빈 행이 있다(301번 51·100번째) |
| 하차 보정 α는 하루 합계 | 시간대별 합계 | 하루 합계로는 시간대 안에서 닫히지 않는다(위 계산 참고) |
| 대응하지 못한 정류장이 있는 패턴은 집계 보류 | 대응 비율 90% 미만일 때만 보류. 빠진 원본 정류장도 누적에는 포함 | 정적 갱신으로 정류소 순서가 자주 바뀐다(2주 사이 107개 노선 중 15개) |
| 새 자료 입력 직후와 매월 초에 다시 집계 | 입력 직후 + 정적 갱신 뒤 매일 | 정류소 순서가 바뀌면 패턴 키가 달라져 다음 집계까지 조회되지 않는다 |
| 통과 횟수 observed = 운행 차량 수 ÷ 편도 소요시간 | 구간별로 실제 지나간 차량을 센다. 원본이 있는 노선의 위치를 상시 수집 | 같은 양을 직접 세는 방법이다. 기점 대기 차량이 섞이지 않고 구간·시간대별 차이가 그대로 나온다 |
| 관리자가 올리는 입력 기능 | CLI만 | 관리자 판별 방식이 정해지지 않았다(`profiles`에 역할 없음). `uploaded_by`는 NULL |
| 평일 전체로 대체 | 평일의 같은 시간대로 대체 | "평일 전체"의 범위가 초안에 정해져 있지 않다 |

## 검증 대기·미결정

- 301번에 탑승해 몇 구간의 재차 인원을 직접 세어 추정값과 대조한다.
- 좌석 수·정원은 초안의 가정값(25·50)이다. 실제 차량 제원으로 교체한다.
- 하차 태그 누락이 정류장마다 고르다는 가정, 한 운행이 같은 시간대 안에서 끝난다는 근사.
- 시간대별 α는 그 시간대에 탄 승객이 같은 시간대에 내린다고 보는 근사다(첫차·막차 시간대는 α가 크게 벗어난다: 5시 5.5, 23시 0.5).
- 명절 연휴의 holiday 포함 여부, 값이 다른 중복 자료의 교체 여부, 단계 코드.
- 안내 인원을 묶는 기준(같은 차량번호, 차량을 모르면 같은 시간대에 고르게), 균형 시뮬레이션의 N·θ와 집계가 없는 노선의
  기준 재차 0 가정은 구현하면서 정한 것이다. 실제 대전 검색으로 시뮬레이션을 돌린 결과는 아직 없다.
- 혼잡 가중치(1.0, 1.0, 1.2, 1.5, 2.0)는 초안의 시작값이며 근거가 없다. 집계가 없는 노선에 비용이 붙지 않아 원본을 입력한
  노선만 순위가 내려가는 점, 이동 중 경로 변경 판단에 혼잡 비용이 빠진 점도 미결정이다.
- 패턴이 여러 개인 노선은 방향을 가를 근거가 원본에 없어 집계를 보류한다(현재 모든 노선이 패턴 1개).
- 위치 관측은 10분 간격이라 하루치만으로는 구간별 값이 한두 대씩 흔들린다. 관측 일수가 쌓여야 안정된다(2026-11-27 기준
  301번은 평일 1~2일분, 토·일은 없음). TAGO 위치 응답에 일부 차량이 빠지는 경우가 있어 실제보다 적게 셀 수 있다.
